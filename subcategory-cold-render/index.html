Subcategory pages: the first server render after cache expiry ships polluted HTML (9 H1s, info-page content inlined)

The first build of a subcategory page after its cached copy expires merges the full content of the info pages (Founder's Message, Terms, Cancellation, Privacy, both languages) into the page HTML. The broken copy is then served to every visitor until the next regeneration. Reproduced today on 5 of 5 quiet subcategories.

Priority: High (SEO) Area: Next.js SSR / ISR, subcategory routes Status: Open Reported: Jul 12, 2026

01Summary

Subcategory pages (e.g. /ar/courts-and-arenas/volleyball-courts/) are cached and periodically regenerated. The first render after the cached copy expires produces HTML that contains the real subcategory content plus the complete server-rendered content of five other pages:

  • Founder's Message (EN + AR)
  • Terms & Conditions (EN + AR)
  • Cancellation Policy (EN + AR)
  • Privacy Policy (EN + AR)

The result is a subcategory page with 9 <h1> tags and thousands of words of legal text that do not belong to the URL. The polluted copy is cached and re-served as-is (verified byte-identical on a repeat request 6 seconds later), then the page heals on a later regeneration (43 seconds later in today's capture).

This looks related to the hydration issue fixed on product pages on July 5, but on the subcategory routes' first server render after revalidation.

02Why this matters

Googlebot is usually the "first visitor" on quiet pages. Low-traffic subcategories sit expired most of the time, so the copy Google downloads is disproportionately the polluted one: 9 H1s, legal-page text mixed into a rental-category URL, and the page's real topic diluted. This directly undermines the subcategory SEO work that shipped this month (unique titles, metas, visible H1s, dedicated sitemaps).

Response headers on the affected route: x-powered-by: Next.js, cache-control: private, no-cache, no-store, max-age=0, must-revalidate. So the polluted copy is produced and briefly re-served by the server-side render/ISR layer, not by a CDN cache.

04How to reproduce

  1. Pick a low-traffic subcategory that has not been visited recently (any of the URLs in the table above).
  2. Request it once and count the H1 tags in the raw response: curl -s -A "Mozilla/5.0" <url> | grep -c '<h1' → expect up to 9.
  3. Request it again within a few seconds → same polluted output (served from cache).
  4. Request it again after ~1 minute → 1 H1, clean page.

Note the pollution window is short, so if a page returns 1 H1 on the first try it was recently visited; try another quiet subcategory.

05Observations that may help locate it

  • The injected content is always the same four info pages, in both locales, in the same order, suggesting a deterministic source (shared layout, prefetched routes, or a cache-key collision during the regeneration build) rather than a random race.
  • Product pages had a similar first-render/hydration issue that was fixed on July 5; subcategory routes appear to have the same class of problem on their first server render after revalidation.
  • The clean and polluted responses differ only by the injected blocks; the real subcategory content (title, meta, H1, product cards) is correct in both.

06Acceptance criteria

The first request to any subcategory page after cache expiry returns exactly 1 <h1> and contains no Founder's Message / Terms / Cancellation / Privacy content. Verifiable with the loop below run against 5+ quiet subcategories after a deploy:

$ for u in aircraft yachts squash-courts parking-spaces volleyball-courts; do
    case $u in
      aircraft|yachts) path="cars-and-vehicles" ;;
      squash-courts|volleyball-courts) path="courts-and-arenas" ;;
      parking-spaces) path="properties" ;;
    esac
    n=$(curl -s -A "Mozilla/5.0" "https://renter.net/ar/$path/$u/" | grep -c '<h1')
    echo "$u: $n h1(s)"
  done
# pass = every line reports exactly 1 h1, including on the first (cold) run
