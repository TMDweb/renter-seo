To build it for all 194 pages, add this function to src/lib/jsonld.tsx. Names are the category and subcategory names from the site menu; English pages use the English names and /en/ addresses:

export function breadcrumbLd(
  locale: "ar" | "en",
  category: { name: string; slug: string },
  subcategory?: { name: string },
) {
  const home = { name: locale === "ar" ? "الرئيسية" : "Home", url: `https://renter.net/${locale}/` };
  const trail = [
    { "@type": "ListItem", position: 1, name: home.name, item: home.url },
    subcategory
      ? { "@type": "ListItem", position: 2, name: category.name, item: `https://renter.net/${locale}/${category.slug}/` }
      : { "@type": "ListItem", position: 2, name: category.name },
  ];
  if (subcategory) {
    trail.push({ "@type": "ListItem", position: 3, name: subcategory.name });
  }
  return { "@context": "https://schema.org", "@type": "BreadcrumbList", itemListElement: trail };
}

Correction 6: unknown addresses answer 404 (done, live since Oct 11)

The subcategory route (src/app/[locale]/(categories)/cars-and-vehicles/[subcategory]/page.tsx, and the same file in the 9 other categories) takes any word after the category as a subcategory. When the word is not a real subcategory, the page still renders and builds its canonical from empty values: https://renter.net/ar + undefined. At the start of the page component and of generateMetadata, look the subcategory up and stop when it does not exist:

import { notFound } from "next/navigation";

// First lines of the page component and of generateMetadata:
const { locale, subcategory } = await params;
const sub = findSubcategory("cars-and-vehicles", subcategory); // the lookup the page already uses for its H1 and meta
if (!sub) {
  notFound();
}

The check must run before the page starts streaming, or the answer stays 200. Next.js: "To return a real 404 status, the resource has to be checked before the response streams." (Next.js: notFound). If the answer is still 200 after the deploy, run the same check in src/proxy.ts.

Why the list holds only the products the server renders, in Google's words

Each Google rule below explains one part of the list design:

Google saysWhat it means for usSource
"Google Search does not interact with your page."Googlebot never scrolls. Products loaded on scroll do not exist for Google, so a client-side update to the JSON-LD would describe products Google cannot see.Lazy-loading content
"Google's crawlers don't 'click' buttons and generally don't trigger JavaScript functions that require user actions to update the current page contents."A "load more" button or scroll trigger is invisible to Google unless it is a real link.Pagination and incremental page loading
"Google Search can understand and process structured data that's available in the DOM when it renders the page."Only what the server renders is read reliably. Keep the block in the server component, as it is now.Structured data with JavaScript
"Your structured data must be a true representation of the page content." and "Don't mark up content that is not visible to readers of the page."The list must equal the products actually rendered in the initial HTML: not fewer, not more.Structured data policies
"Give each chunk its own persistent, unique URL", "using ?page=12", "Link sequentially to the individual URLs", "give each page its own canonical URL."If every product must be reachable through category pages, add paginated URLs. Each one is server-rendered with its own product set and its own ItemList.Both docs above

Also true, and it lowers the stakes: every product page already carries its own Product block and is in the sitemap and the Merchant feed. The category ItemList is a map, not the only road. Google shows list rich results only for courses, movies, recipes and restaurants, so this block earns no visual change; its value is machine readability.

Part 2, later: paginated addresses

Not urgent. Today ?page=2 shows page 1 with a canonical to page 1, which is harmless. Build this when convenient:

  • Serve /ar/cars-and-vehicles/?page=2, ?page=3 and so on from the server with the next set of products. Each page has its own H1, its own self-referencing canonical (?page=2 points to ?page=2, not to page 1) and its own list block of that page's products.
  • Add a real <a href="…?page=2"> link at the end of the grid. It can be the "load more" control itself. Keep infinite scroll for users and update the address bar with the History API, as Google's documentation describes.
  • Do not use rel="next" or rel="prev"; Google no longer reads them.
