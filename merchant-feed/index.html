1. Why this ticket exists #

We ran a manual test: a Merchant Center account with only 10 products added by hand. Result, without any ad spend:

79
Organic clicks from Google Shopping
7 / 10
Test products that received clicks
938
Active products at ticket creation (2026-07-05 sitemap count)

Scaling this to the full catalog needs a data feed, not manual entry. This is separate from the XML sitemap: the sitemap tells Google which pages exist, the merchant feed carries structured product data (price, availability, images) for Shopping listings, and later enables paid Shopping campaigns.

Known policy risk: rentals (read before building)

Google's unsupported-content policy for Shopping ads and free listings prohibits "Services: labor, time, effort, expertise, or actions, which do not result in ownership of a tangible product." Rentals do not transfer ownership, so rental offers sit in a policy grey zone (older versions of this policy named "equipment rentals" explicitly). Our 10-product test surviving so far is not a policy clearance. We proceed anyway: item-level or account-level disapprovals are a possible outcome, Saiaf owns monitoring and response, and this risk does not change what Paulo builds.

2. Approach #

Same pattern as the sitemap route: one new App Router route handler that renders XML straight from the products API. This is the documented Next.js way to serve a custom .xml URL (see the app/rss.xml/route.ts example in the route handlers reference); product feeds have no built-in metadata-route convention like sitemap.xml does. 

src/app/merchant-feed-ar.xml/route.ts   →   https://renter.net/merchant-feed-ar.xml

Heads-up: this URL already errors today

https://renter.net/merchant-feed-ar.xml currently returns HTTP 500 (with text/html), not 404. Check what is intercepting that path before assuming a clean slate.

Implementation requirements

  • Include all eligible products (definition in section 3), pulled live from the same source the sitemap uses.
  • Caching: add export const revalidate = 3600 (a literal number) to the route handler. GET route handlers are dynamic by default in Next 15+, so without this export the feed rebuilds on every request. The handler must not read the request object, headers(), or cookies(), or revalidation is silently disabled. (If the project later enables Cache Components in Next 16, this becomes use cache + cacheLife.)
  • Response headers: return the XML with an explicit Content-Type: application/xml; charset=utf-8 (matching the live sitemaps). Without it, the body is served as text/plain: 
    return new Response(xml, {
  headers: { "Content-Type": "application/xml; charset=utf-8" },
});
  • Verification note: production currently serves cache-control: s-maxage=31536000 (one year) on /sitemap.xml, which suggests the sitemap's intended 6-hour revalidation is not reaching the response (fully static route or an nginx override). Confirm the feed's revalidate actually shows up in the response headers, and check the sitemap while you are at it.
  • Merchant Center side: Saiaf registers the URL as a file data source with a scheduled daily update (current Merchant Center Next terminology). Google re-downloads the feed every 24 hours.
  • Start with one Arabic feed (content language ar, target country SA). An English feed can be added later as a second file.

Freshness, stated honestly

End-to-end latency for an add, removal, or price change is up to ~25 hours: up to 1 hour for the feed cache (revalidate = 3600) plus up to 24 hours until Google's next scheduled fetch. There is no "instant" removal in this architecture; that is normal and accepted. Phase 2 (out of scope): push updates in near real time via the Merchant API. Note: the older Content API for Shopping sunsets on August 18, 2026, do not build anything on it.

3. Data rules (resolve ambiguity before coding) #

QuestionRule
What is an "eligible product"? A listing that is currently published and publicly visible on the site (same source and filter as the sitemap's product list). Products that are unavailable but still published stay in the feed with g:availability = out_of_stock. Unpublished or lessor-deleted products drop out entirely.
Missing image or price Skip the product (Google rejects items without image_link or price) and count it. The route should expose the skip count in an XML comment at the top of the feed, e.g. <!-- items: 912, skipped: 26 -->, so Saiaf can see coverage at a glance.
Long titles / empty descriptions Truncate titles longer than 150 characters at 147 + "...". If the description is empty, fall back to the title. Escape XML entities in all text fields.
Which price for multi-duration rentals? Emit the per-day price. If a product has no per-day price, emit the lowest-duration price displayed on the product page. Confirm the exact API field with the backend at kickoff. Transient feed-vs-page mismatches within the 1-hour cache window after a price edit are expected and excluded from acceptance.
Which slug? The same slug field the sitemap and product links use. Open question for Paulo to answer in this ticket: when a lessor edits a title, does the slug change, and does the old URL 301? (A stale feed may carry old slugs for up to ~25 hours.)
ID stability Assumption to confirm with the backend team: product IDs are never reused after deletion. Google permanently associates g:id with an item's history. If IDs can be recycled, flag it before launch.
Source of g:product_type Arabic category and subcategory names from the products API, joined as category > subcategory (separator: space, greater-than, space). Confirm the API exposes both names; if only IDs, join against the category tree.

4. Spec: fields per product #

AttributeValue for RenterNotes
g:id Numeric product ID, e.g. 2213 Stable, never reused (see section 3)
g:title Product name (AR) Max 150 chars, truncation rule in section 3
g:description Product description, plain text Strip HTML, fallback rule in section 3
g:link https://renter.net/ar/product/{id}/{slug}/ Final URL with trailing slash, must return 200 directly, no redirect hop
g:image_link Main product image URL Min 500x500 px (Google enforces 500x500 for all products from Jan 31, 2027; the old 250x250 apparel minimum is gone, do not ship smaller). Recommend ~1500x1500. No watermarks or logo overlays. Extra images via g:additional_image_link, up to 10, one tag each
g:availability in_stock / out_of_stock Drive from real product status
g:price e.g. 150.00 SAR Number + ISO 4217 code. Must match the page per the pricing rule in section 3. Mismatch is the #1 disapproval reason
g:condition used Allowed values are new / refurbished / used; rentals are generally "used", new only where truly new
g:brand + g:identifier_exists Brand when known; identifier_exists = false only when the item truly has no GTIN/MPN/brand Brand is optional here because the items are used (brand is required only for new products). Do NOT blanket-set identifier_exists=false on visibly branded items (designer dresses, Sony/Zeiss gear): Google issues warnings when it detects identifiers that were declared absent. If the API has a brand field, emit it
g:product_type Renter category path, e.g. أزياء وملابس > فساتين Optional but helps Google classify; source rule in section 3

5. Feed template (RSS 2.0 with the Google namespace) #

Matches Google's current RSS 2.0 sample: g:-prefixed attributes at item level, plain title/link/description only at channel level. Bidi warning: Arabic inside this LTR code block can display visually reordered around the &gt; separator. The logical byte order is category first, then subcategory. Trust the template text, not how it looks on screen. 

<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0" xmlns:g="http://base.google.com/ns/1.0">
  <channel>
    <title>Renter</title>
    <link>https://renter.net/ar/</link>
    <description>Renter product feed</description>

    <item>
      <g:id>2213</g:id>
      <g:title>فستان ناعم</g:title>
      <g:description>فستان ناعم للإيجار، يلبس سمول، بحالة ممتازة.</g:description>
      <g:link>https://renter.net/ar/product/2213/fstan-naam/</g:link>
      <g:image_link>https://renter.net/images/products/2213/main.jpg</g:image_link>
      <g:availability>in_stock</g:availability>
      <g:price>150.00 SAR</g:price>
      <g:condition>used</g:condition>
      <g:identifier_exists>false</g:identifier_exists>
      <g:product_type>أزياء وملابس &gt; فساتين</g:product_type>
    </item>

  </channel>
</rss>

One <item> per eligible product. This example item has no brand; branded items add <g:brand> and drop identifier_exists.

6. Failure behavior and monitoring #

A broken feed at Google's fetch time can drop the entire catalog from Shopping. Two rules:

  • Never serve an empty or error feed. If the products API is down, times out, or returns drastically fewer items than the previous render (sanity check: less than 50% of the last count), serve the last good render instead and log the incident. A stale feed is harmless; an empty one deletes all listings.
  • Monitoring split: Saiaf checks the data source's fetch status in Merchant Center after each of the first 3 scheduled fetches, then weekly. Paulo makes route errors visible in whatever logging the app already has, so a persistent 500 is noticed within a day, not a month.

7. Acceptance criteria #

1 to 5 are verifiable by Paulo alone; 6 is Saiaf's check with a committed turnaround.

  • https://renter.net/merchant-feed-ar.xml returns HTTP 200 with Content-Type: application/xml; charset=utf-8 and well-formed XML (passes an XML validator).
  • Item count equals the number of eligible products that meet minimum data requirements, and the skip count appears in the feed comment (section 3 rules).
  • Spot-check of 20 random g:link URLs: every one returns 200 directly, trailing slash included, no redirect hop.
  • Add/remove test: unpublish a test product, it disappears from the feed within 1 hour (the revalidate window). Google-side propagation of up to a further 24 hours is expected and out of scope.
  • Failure drill: with the products API unreachable (or mocked to fail), the route serves the last good feed, never an empty feed or a 500.
  • Saiaf, within 1 business day of deploy: the first scheduled fetch in Merchant Center completes with zero feed-level (file) errors. Item-level policy disapprovals are expected (see the rentals risk note) and are Saiaf's to handle, they do not fail this ticket.
