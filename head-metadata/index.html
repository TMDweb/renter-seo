Renter × TMD · Dev Ticket · July 26, 2026 · updated August 10, 2026

Head template and redirects: five faults. No Open Graph tags, no Twitter Card tags, no structured data, relative canonical URLs, and 307 redirects on 57% of the clicks from search.

Five faults in the shared <head> template and the routing layer. Each fault is one change that corrects all pages. Measured on the same 12 live URLs on Jul 26, Aug 5 and Aug 10.

Priority: High (SEO + social) Area: Next.js metadata / head template, middleware Status: Open Reported: Jul 26, 2026
01

Summary

Status, measured Aug 10: Open Graph, Twitter Cards and the home-page hreflang are done. The double encoding is nearly done (40% → 2% of sampled product pages). Open: the product JSON-LD has three faults (Fix 3), the other page types have no JSON-LD (Fix 3), canonical URLs are still relative on 7 of 12 test pages (Fix 4), and the redirects still return 307 and now carry 59.4% of all search clicks (Fix 5).

All faults are template-level: one change corrects all pages, so they are grouped in one ticket.

SCOPE. The URL lists in this ticket are test samples, not the full list. Each fix states its own scope. The sitemap has 2,280 pages: 2,072 product, 194 category and subcategory, 14 information.
The five faults, status Aug 10
  1. No Open Graph tags — done.
  2. No Twitter Card tags — done.
  3. Structured data: Product live with three faults; other page types have none — open, see Fix 3.
  4. Relative canonical URLs (home-page hreflang: done) — open, see Fix 4.
  5. 307 redirects, 59.4% of search clicks — open, see Fix 5. Do this first.
02

Why these faults are important

  • Redirects (biggest): 59.4% of all search clicks land on a 307 URL, so Google holds the ranking signals there instead of passing them to the real page.
  • Open Graph: without it a shared link shows no image and no title. Renter grows through WhatsApp and social. Done Aug 10.
  • Structured data: without it Google cannot show price or availability, and AI search tools cannot read the products.
  • Canonical: Google asks for absolute URLs. hreflang is absolute; canonical in the same <head> is not.

Fix 1 and 2: Open Graph and Twitter Card tags

Done Aug 10. Verified on all 12 test pages, with absolute image URLs. Kept for reference.

Add these tags to the shared metadata of each route. Use the data that the page has already. In the Next.js App Router, use the openGraph key and the twitter key of the Metadata object. You can set them one time in the root layout. Then you can change them for each route.

Product pages, using existing listing fields:

<meta property="og:type"        content="product" />
<meta property="og:site_name"   content="Renter" />
<meta property="og:locale"      content="ar_SA" />   <!-- en_US on /en/ -->
<meta property="og:title"       content="{page title}" />
<meta property="og:description" content="{meta description}" />
<meta property="og:url"         content="https://renter.net{path}" />
<meta property="og:image"       content="https://renter.net{first listing image}" />
<meta property="og:image:width"  content="1200" />
<meta property="og:image:height" content="630" />

<meta name="twitter:card"        content="summary_large_image" />
<meta name="twitter:title"       content="{page title}" />
<meta name="twitter:description" content="{meta description}" />
<meta name="twitter:image"       content="https://renter.net{first listing image}" />

Notes about how the card shows:

  • Make og:image an absolute URL. WhatsApp and Facebook cannot read a relative path.
  • Use one default image for the site. Some pages have no photo: the info pages, the category pages, and approximately 67 old listings with bad images. The default image prevents an empty card.
  • Make each image 1200x630 or larger. Also make each file smaller than approximately 300 KB. WhatsApp frequently shows no card for a larger file.

3b. Product page: one block

UPPERCASE values map to these fields, verified in the page's own data payload on Aug 10:

TokenField
PRODUCT_TITLEtitle
PLAIN_TEXT_DESCRIPTIONdescription, tags stripped, entities decoded
ABSOLUTE_IMAGE_URLSpost_images[].image
LISTING_IDid
FULL_LISTING_URLthe page's canonical URL (id + slug)
PRICE_NUMBERpost_lease_terms[].price, as a number. If the listing has more than one lease term, use the one the page shows as its price
RENTAL_UNITpost_lease_terms[].lease_term → daily = "DAY" (verified), hourly = "HUR", weekly = "WEE", monthly = "MON"
AVERAGE_RATING / REVIEW_COUNTreview_summary.review_average / review_summary.review_count
REVIEWER_NAME, REVIEW_DATE_YYYY_MM_DD, REVIEW_STARS, REVIEW_TEXTnot verified: every sampled product has review_count: 0, so the single-review object never appears in the payload. Map these from the reviews API

Rules:

  • availability: API AVAILABLE → https://schema.org/InStock. Any other value → remove offers.
  • RENTAL_UNIT from the listing's rental period: hour "HUR", day "DAY", week "WEE", month "MON".
  • Price 0 or 1 SAR is a placeholder → remove offers.
  • Zero reviews → remove aggregateRating and review. One real review is enough to keep them (agreed Aug 10). Never invent a review. List every review in the array.
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": PRODUCT_TITLE,
  "description": PLAIN_TEXT_DESCRIPTION,
  "image": [ ABSOLUTE_IMAGE_URLS ],
  "sku": LISTING_ID,
  "url": FULL_LISTING_URL,
  "offers": {
    "@type": "Offer",
    "url": FULL_LISTING_URL,
    "priceCurrency": "SAR",
    "price": PRICE_NUMBER,
    "availability": "https://schema.org/InStock",
    "priceSpecification": {
      "@type": "UnitPriceSpecification",
      "price": PRICE_NUMBER,
      "priceCurrency": "SAR",
      "referenceQuantity": { "@type": "QuantitativeValue", "value": 1, "unitCode": RENTAL_UNIT }
    }
  },
  "aggregateRating": {
    "@type": "AggregateRating",
    "ratingValue": AVERAGE_RATING,
    "bestRating": 5,
    "ratingCount": REVIEW_COUNT
  },
  "review": [
    {
      "@type": "Review",
      "author": { "@type": "Person", "name": REVIEWER_NAME },
      "datePublished": REVIEW_DATE_YYYY_MM_DD,
      "reviewRating": { "@type": "Rating", "ratingValue": REVIEW_STARS, "bestRating": 5 },
      "reviewBody": REVIEW_TEXT
    }
  ]
}
</script>
